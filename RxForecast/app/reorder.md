# Reorder Queue — Computation Reference

**Scope:** this documents exactly how every number and badge on the Reorder Queue (list view + detail drawer) is computed **in the current prototype**, grounded directly in the code — not the production spec. Where the prototype's approach differs from what `lld.md`/`engg.md` FEATURE_1 actually calls for production, that's flagged explicitly in §6, same convention as `GAPS.md`.

Source files referenced throughout:
- [`backend/src/lib/priority.js`](./backend/src/lib/priority.js) — urgency scoring
- [`backend/src/lib/orderQty.js`](./backend/src/lib/orderQty.js) — recommended quantity, including `custom_par_level` rule resolution
- [`backend/src/lib/overrideRules.js`](./backend/src/lib/overrideRules.js) — the buyer-override lookup `orderQty.js` consults
- [`backend/src/lib/forecasting.js`](./backend/src/lib/forecasting.js) — 7-day forecast + confidence band
- [`backend/src/routes/queue.js`](./backend/src/routes/queue.js) — assembles the queue row, filtering/sorting
- [`backend/src/routes/forecast.js`](./backend/src/routes/forecast.js) — the detail drawer's forecast + citations
- [`backend/src/data/loader.js`](./backend/src/data/loader.js) — where the raw numbers come from

## 1. Raw data sources

Everything below is computed from four CSVs, loaded once at server boot (`loader.js`) from `backend/seed-data/` — a trimmed, committed copy of the full external `RxForecast_SyntheticData/` dataset (added 2026-08-22 so the app can actually be deployed; see `scripts/export-seed-data.mjs`):

| File | What it provides | Loaded as |
|---|---|---|
| `formulary.csv` | Drug identity, category, DEA schedule, TE code, **velocity tier (A/B/C)** | Full file, filtered to the demo's ~60-NDC trimmed set |
| `dispense_history.csv` | Daily dispensed quantity per store/NDC | **Trailing 150 days only** (`minDate: '2025-08-01'`), filtered to demo stores/NDCs — not the full 24-month/1.27M-row file |
| `inventory_snapshot_weekly.csv` | On-hand qty, in-transit qty, reorder point (days), target days-of-supply, per store/NDC | Most recent snapshot per store+NDC key |
| `fda_ashp_shortage_events.csv` | Active/resolved shortage records | Used only to compute the `shortageLinked` flag (§2) |

The demo NDC set is capped at 60: every velocity-tier-A NDC, plus anything involved in a shortage/substitution/override (so those flows always have real data). This is the trimmed scope noted throughout `GAPS.md`.

## 2. Queue list — one row per store+NDC

Assembled by `buildQueueRow()` in `queue.js`:

| Column | Computation |
|---|---|
| **Drug / Brand / Category** | Direct lookup from `formulary.csv` — no computation |
| **On hand** | `inventory.onHand + inventory.inTransit` (null if no inventory snapshot exists for that store+NDC) |
| **Days of supply** | See §4.1 — `onHand ÷ avgDailyUsage` |
| **Qty to order** | See §4.2 — the editable, pre-filled recommendation |
| **Urgency badge** (HIGH / MEDIUM / LOW) | See §4.1 — banded off days-of-supply vs. reorder point |
| **Shortage badge** | `true` if any record in `fda_ashp_shortage_events.csv` has this NDC and `status === 'Current'` (or the demo's relabeled-active equivalent — see `GAPS.md` "AI reasoning") |
| **Sch. II badge** | `formulary.deaSchedule === 2` — a static formulary fact, not computed |

### What determines whether a row appears at all

From `queue.js`'s `GET /` handler, in order:

1. **Store scope** — a PIC's `store_id` is forced to their own store server-side, overriding any query param
2. **Deferred-by-this-user rows are skipped** — cleared the next time that specific user logs in (not a scheduled job in this prototype)
3. **Permanently-rejected rows are skipped** — `reject` is a distinct, permanent decision (unlike defer)
4. **Duplicate suppression** — skipped if an open (non-rejected/cancelled) PO already covers that store+NDC
5. **Low-urgency rows are hidden unless shortage-linked** — only `medium`/`high` urgency, or any shortage-linked row regardless of urgency, actually reaches the table
6. **Sort** — descending by `priorityScore` (§4.1), so the highest-risk items are always at the top

## 3. Detail drawer — additional fields beyond the list

Opening a row calls `GET /api/queue/:key/detail`, which returns everything the list row has **plus**:

| Field | Computation |
|---|---|
| **7-day forecast: Forecast / Low / High** | See §4.3 — from `GET /api/forecast/:storeId/:ndc`, called separately by the drawer |
| **"Why?" citations** | Three fixed entries generated by `forecast.js`: (1) dispense-event count and window used, (2) the inventory snapshot's on-hand/in-transit numbers, (3) an explicit label that this is the prototype's trailing-average model, not the production forecaster |
| **Recommended order qty (editable)** | Same `recommendedQtyFromForecast()` as the list — one function shared by both, so they can't drift apart |
| **Schedule II block** | If `deaSchedule === 2`, the drawer replaces the order form entirely with a hard "manual order required" notice — no qty/approve UI at all. This is deterministic code, not a model judgment call |

## 4. The actual formulas

### 4.1 Urgency (`priority.js`)

```
daysOfSupply   = (onHand + inTransit) / avgDailyUsage
reorderPoint   = inventory.reorderPointDays  (default 10 if missing)
stockoutRisk   = max(0, (reorderPoint − daysOfSupply) / reorderPoint)     // 0 .. 1+
tierWeight     = A: 1.5   B: 1.1   C: 0.8    (velocity tier)
priorityScore  = round(stockoutRisk × tierWeight × 100, 2 decimals)

band = "high"    if daysOfSupply < reorderPoint × 0.5
       "medium"  if daysOfSupply < reorderPoint
       "low"     otherwise
```

**Deliberately excluded: dollar margin.** This isn't an oversight — `PRD.md`'s Fairness section requires margin data be kept out of ranking/reasoning inputs, so the queue can't implicitly steer a buyer toward higher-margin brand-name orders. Velocity tier is used as the weighting signal instead, same mitigation intent.

If there's insufficient forecast data (see §4.3), `priorityScore = 0` and `band = "insufficient_data"` — the row still shows, flagged, rather than silently defaulting to a real-looking urgency.

**Worked example** (illustrative numbers): onHand+inTransit = 12, avgDailyUsage = 2/day → daysOfSupply = 6. reorderPointDays = 10. stockoutRisk = (10−6)/10 = 0.4. Tier A → priorityScore = 0.4 × 1.5 × 100 = **60**. Since 6 < 10×0.5=5 is false but 6 < 10 is true → band = **medium**.

### 4.2 Recommended quantity (`orderQty.js`)

```
recommendedQty = max(0, round(avgDailyUsage × targetDaysOfSupply − onHand))
```

`targetDaysOfSupply` comes from the inventory record (defaults to 21 days if unset) — **unless an active `custom_par_level` buyer override rule exists for this NDC+store, in which case the rule's value wins** (wired 2026-08-19, see `rule.md` §5). `orderQty.js`'s `resolveTargetDays()` is the resolution point; the queue row's `parLevelSource` field (`'rule'` or `'default'`) tells the UI which one actually applied, shown as a small "rule" indicator next to the qty field. Plain-language: *"how much do I need to reach my target buffer, given what's already on hand or already inbound."*

### 4.3 7-day forecast (`forecasting.js`)

A **trailing-average model with a statistical confidence band** — not a trained ML model (see §6).

```
avgDailyUsage   = total qty dispensed / number of days spanned by the dispense history
forecastQty7d   = avgDailyUsage × 7
stddev          = sample standard deviation of daily dispensed quantities
band            = stddev × √7          (how variance scales summing 7 independent days)
confidenceLow   = max(0, forecastQty7d − band)
confidenceHigh  = forecastQty7d + band
```

If there are fewer than 30 days of dispense history for that store+NDC, the forecast returns `insufficientData: true` instead of numbers — this is what triggers the drawer's cold-start fallback message rather than a confident-looking forecast built on too little data.

## 5. Data flow, end to end

```
dispense_history.csv ──┐
                        ├──▶ avgDailyUsage ──▶ forecastQty7d, confidenceLow/High (§4.3)
                        │                  └─▶ daysOfSupply (§4.1) ──▶ urgency band
inventory_snapshot.csv ─┤
                        └──▶ recommendedQty (§4.2)
formulary.csv ──────────────▶ velocity tier (urgency weight), category, DEA schedule, TE code
fda_ashp_shortage_events.csv ▶ shortageLinked flag ──▶ keeps otherwise-low-urgency rows visible
```

## 6. Known simplifications vs. the production spec

Everything above is **real, computed math on real (synthetic) data** — none of it is canned or hardcoded per-row. But it's a deliberately simpler stand-in for what `lld.md`/`engg.md` FEATURE_1 actually specify for production:

| This prototype | Production spec |
|---|---|
| Trailing-average + stddev-based confidence band | Trained LightGBM model, monthly retrain, backtested MAPE accuracy (`lld.md` §4.2) |
| 150-day dispense window, ~60-NDC formulary | 24-month history, full ~8,000-SKU formulary (`PRD.md` Appendix B) |
| Priority score computed on every request | A materialized view (`v_reorder_queue`) refreshed nightly, per `lld.md` §3.2 |
| Defer resurfaces on that user's next login | Resurfaces on the next scheduled nightly cycle, chain-wide (`engg.md` FEATURE_1) |

Full severity-tiered gap list: `GAPS.md`.
